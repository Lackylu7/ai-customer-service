# 可重复交付的单企业电商客服设计

## 1. 目标

把当前以“星河优选”为演示企业的本地 AI 客服项目，改造成一套可以为不同电商企业重复部署的单企业交付版本。每次交付使用同一套代码，企业名称、客服文案、Dify 资源名称和 Chatwoot Inbox 等通过配置文件确定；企业数据、密钥和运行状态仍按部署实例隔离。

本阶段的成功标准是：复制企业配置模板、填写一家商家的信息并执行一条初始化命令后，系统能创建或复用该实例所需的 Dify 与 Chatwoot 资源，生成客户聊天入口，并通过现有 RAG、人工转接和运营闭环验收。

## 2. 已确认决策

- 首个真实试点继续选择电商行业。
- 第一阶段采用“企业配置文件 + 自动初始化脚本”，不建设商家自助网页向导。
- 每家企业独立部署一套应用和数据，不在同一运行实例中共享知识库、会话数据库或第三方密钥。
- “星河优选”保留为演示企业配置和样例资料，不再作为业务代码中的固定名称。
- 第一阶段完成本地通用化与交付验收后，再部署到中国内地服务器。
- 项目进入 Git 版本管理，密钥、企业本地配置、数据库、日志、截图和第三方运行目录不得进入版本库。

## 3. 范围

### 3.1 本阶段包含

- 企业配置文件、严格校验和安全加载。
- 企业名称、客服文案、Dify 资源名称、Chatwoot Inbox 和网页组件的配置化。
- 幂等的企业初始化脚本，复用现有 Dify、Chatwoot 和运营配置脚本。
- 星河优选演示配置和电商资料继续可用。
- 客户演示服务启动检测修复，以及统一的本地启动和状态检查入口。
- 端到端知识缺口测试的随机误报修复。
- 配置、脚本、业务回归、RAG、端到端和浏览器验收。
- 企业交付、资料准备、启动、验收和故障排查文档。

### 3.2 本阶段不包含

- 多企业共享一个应用实例。
- 企业在线注册、商家自助后台、RBAC、SSO、套餐和计费。
- 自动申请 DeepSeek、Dify 或 Chatwoot 的管理员凭证。
- 微信、邮件、WhatsApp、语音和图片识别等新渠道。
- 中国内地服务器、域名、备案、HTTPS 和生产数据库迁移；这些属于下一阶段。

## 4. 配置模型

新增受版本控制的 `config/enterprise.example.json`，内容是一份可运行的星河优选演示配置。接入真实企业时复制为被 Git 忽略的 `config/enterprise.local.json`，再通过 `.env` 中的 `ENTERPRISE_CONFIG_PATH` 指向它。

配置结构固定为：

```json
{
  "schema_version": 1,
  "company": {
    "name": "星河优选",
    "industry": "ecommerce",
    "website_url": "http://127.0.0.1:8000"
  },
  "assistant": {
    "name": "星河优选 AI 客服",
    "welcome_title": "你好，欢迎咨询星河优选",
    "welcome_message": "请告诉我你想了解的商品、物流或售后问题。",
    "handoff_message": "正在为你转接人工客服，请稍候。"
  },
  "dify": {
    "dataset_name": "星河优选客服知识库",
    "app_name": "星河优选 AI 客服",
    "indexing_technique": "economy"
  },
  "chatwoot": {
    "inbox_name": "星河优选网站客服",
    "widget_color": "#1f6feb"
  },
  "locale": "zh_CN",
  "business_timezone": "Asia/Shanghai"
}
```

配置文件不得包含 `api_key`、`token`、`password`、`secret` 等认证字段。DeepSeek、Dify、Chatwoot 和运营密钥继续仅存放在被 Git 忽略的 `.env` 中。

校验规则如下：

- `schema_version` 必须为整数 `1`。
- 第一阶段 `company.industry` 只接受 `ecommerce`。
- 企业、客服、知识库、应用和 Inbox 名称去除首尾空白后必须为 1–100 个字符。
- 欢迎语和转人工文案必须为非空文本，单项不超过 500 个字符。
- `website_url` 必须是 `http` 或 `https` URL；本地允许 `127.0.0.1`，生产阶段再要求 HTTPS。
- `widget_color` 必须是六位十六进制颜色。
- `indexing_technique` 只接受 `economy` 或 `high_quality`。
- `locale` 第一阶段固定为 `zh_CN`，时区固定为 `Asia/Shanghai`。
- 出现未知字段或缺少必填字段时直接失败，错误信息指出字段路径但不回显任何密钥。

## 5. 组件边界

### 5.1 企业配置模块

新增 `app/enterprise_config.py`，使用 Python 标准库 `json`、`dataclasses` 和 `urllib.parse` 读取并校验配置，输出不可变的 `EnterpriseConfig`。它同时提供命令行校验入口，使 PowerShell 初始化脚本和 Python 运行时共用同一套规则，避免两份校验逻辑漂移。

AI 编排服务只消费运行时需要的配置，例如人工转接文案；Dify、Chatwoot 和网页组件的名称由初始化脚本消费。现有 `.env` 配置仍由 `app/settings.py` 负责，企业配置与密钥配置不合并成一个对象。

### 5.2 企业初始化脚本

新增 `scripts/configure-enterprise.ps1`，接口为：

```text
configure-enterprise.ps1 -ConfigPath <path> [-EnvPath <path>] [-ValidateOnly]
```

执行顺序：

1. 使用项目虚拟环境调用 `app.enterprise_config` 校验配置。
2. 确认 `.env` 存在且 Dify、Chatwoot 必需的管理员侧配置已提供；只报告缺少的变量名称。
3. 创建或复用当前部署实例的 Dify 知识库，并把资源 ID 安全写入 `.env`。
4. 导入或更新客服 Chatflow，使用配置中的应用名称、知识库和人工转接文案。
5. 创建或复用 Chatwoot Website Inbox、签名 Webhook 和 `ai_handoff` 标签。
6. 渲染包含当前企业名称、欢迎语、颜色和 Website Token 的客户演示页。
7. 写入 `ENTERPRISE_CONFIG_PATH`，重启服务后由运行时加载。
8. 输出不含 ID 密钥和 Token 的完成摘要及下一条安全启动命令。

脚本必须幂等：同一配置重复执行时更新或复用资源，不能创建同名重复应用、知识库或 Inbox。`-ValidateOnly` 只校验文件和依赖条件，不写 `.env`、不创建第三方资源。

### 5.3 现有脚本兼容

`provision-dify-chatflow.ps1`、`configure-dify-knowledge.ps1`、`configure-chatwoot.ps1` 和对应 Python/Ruby 辅助脚本增加明确的名称或配置参数，默认读取 `ENTERPRISE_CONFIG_PATH`。未显式配置路径时使用 `config/enterprise.example.json`，确保当前星河优选演示流程继续可运行。

已有脚本继续支持单独执行，企业初始化脚本只负责按固定顺序编排它们，不复制第三方 API 逻辑。

## 6. 运行时数据流

企业资料处理链路保持不变：

```text
企业资料 -> Docling -> Markdown -> 当前部署的 Dify 知识库
```

在线客服链路保持不变，仅将企业文案改为配置值：

```text
客户网页 -> Chatwoot -> FastAPI 编排服务 -> Dify Chatflow -> DeepSeek
                                      \-> 风险/知识不足 -> Chatwoot 人工坐席
                                      \-> 运营事件/知识缺口 -> 运营看板
```

单企业部署意味着一个运行实例只加载一个 `EnterpriseConfig`、一个 Dify 数据集与应用、一组 Chatwoot 资源和一个本地状态数据库。任何请求都不能通过参数选择另一家企业。

## 7. 启动与状态检查

新增统一的本地启动脚本，按依赖顺序检查或启动 Dify、Chatwoot、AI 服务和客户演示页；新增状态检查脚本，报告四个入口是否可访问，但不输出认证信息。

`run-widget-demo.ps1` 不再仅凭 PID 文件判断服务存在：

- 先检查 `127.0.0.1:8000` 是否响应且页面含本项目标记，符合时报告已运行。
- 端口被其他程序占用时失败并给出明确提示，不终止未知进程。
- 端口空闲时启动静态服务器并轮询页面就绪。
- PID 文件只作为诊断信息，不作为在线状态的唯一依据。

## 8. 端到端测试稳定性

现有 E2E 测试在知识缺口问题中嵌入随机 GUID，然后用完整 GUID 查找缺口。GUID 偶尔包含 12–19 位连续数字，会被隐私规则正确识别为卡号并脱敏，导致测试误报。

修复后使用本次创建的 Chatwoot `conversation_id` 匹配知识缺口的 `last_conversation_id`，并继续断言：

- 事件结果为 `handed_off/knowledge_gap`。
- 恰好创建一个待处理缺口。
- 首次出现次数为 1。
- 状态和备注可以更新。

不削弱生产脱敏规则，也不为测试文本增加隐私处理例外。

## 9. 错误处理与安全

- 配置解析、字段校验或依赖检查失败时，初始化立即停止，尚未执行的外部操作不得继续。
- 第三方资源创建成功但后续步骤失败时，重复执行必须能从已有资源继续，不要求人工删除资源。
- `.env` 更新继续采用现有安全写入模式，不在命令参数、标准输出或日志中携带密钥。
- 企业本地配置虽然不含密钥，仍默认忽略，避免未公开的企业名称、网址和客服文案被提交。
- HTML 渲染必须对企业可配置文本做安全转义；客户端动态内容继续使用 `textContent`。
- 初始化和状态检查不得关闭、删除或重建现有 Dify、Chatwoot 和数据库资源。

## 10. 测试与验收

### 10.1 配置测试

- 完整示例配置加载成功。
- 缺少字段、未知字段、错误类型、非法 URL、非法颜色和过长文案失败。
- 配置对象及异常不包含 `.env` 密钥。
- `-ValidateOnly` 不修改 `.env` 或运行目录。

### 10.2 脚本测试

- 企业配置路径安全写入临时 `.env`。
- 重复执行使用同一资源名称，不生成重复配置行。
- 缺少依赖变量时只显示变量名称。
- Widget 服务离线、已在线和端口被其他服务占用三种状态行为明确。

### 10.3 回归验收

- Python 单元测试、编译检查和依赖检查全部通过。
- PowerShell 配置脚本测试全部通过。
- Dify Chatflow DSL 验证通过。
- RAG 评测保持 8/8。
- Chatwoot 真实端到端测试连续执行不再发生随机误报。
- 运营看板浏览器验收通过桌面和 360px 移动布局。
- 星河优选演示配置可以完整初始化并回答现有样例问题。

## 11. 第一家真实商家交付流程

1. 从模板复制 `config/enterprise.local.json`，填写商家公开品牌信息。
2. 收集商品说明、物流、退款、售后、投诉升级和人工客服工作时间等资料。
3. 执行配置校验和企业初始化脚本。
4. 使用 Docling 清洗并导入资料。
5. 建立不少于 30–50 条真实问题的评测集，覆盖标准问法、口语化问法、连续追问、知识不足和风险场景。
6. 验收 RAG、人工转接、Chatwoot 坐席和运营闭环。
7. 本地验收稳定后进入中国内地服务器部署、备案、HTTPS、安全加固和灰度试运营阶段。

## 12. 后续演进

只有当至少一家真实商家完成灰度试用并产生可分析的客服数据后，才评估多租户 SaaS。届时需要单独设计租户身份、数据隔离、自动资源编排、RBAC、配额、计费和共享基础设施，不在本设计上直接叠加。
