# 人工接管 SLA、AI 安全托底与恢复设计

## 1. 目标

补齐当前客服系统在人工接管后的两个业务缺口：

1. 人工客服中途无法继续回复时，客户不能长期处于完全无人响应状态。
2. 管理员需要在运维看板中安全、直观地把指定会话恢复为 AI 接管，而不再运行本地脚本。

本设计保留“人工优先”的原则。AI 超时托底不是自动结束人工接管；只有管理员或客服主管明确执行“恢复 AI”后，会话才正式回到 AI 模式。

## 2. 已确认的业务规则

- 人工接管会话由管理员、客服主管或持有 `OPERATIONS_API_KEY` 的授权人员管理。
- 客户在人工模式发送新消息后，人工客服拥有 5 分钟优先回复时间。
- 5 分钟内出现有效人工公开回复时，本轮 AI 托底取消。
- 5 分钟无人回复时：
  - 普通知识库问题允许 AI 临时托底回答，但会话继续保持人工模式。
  - 投诉、法律、支付安全、账户安全、主动要求人工、知识缺口或 Dify 故障只发送等待提示，不生成业务答案。
- 同一会话的自动等待提示和托底回复受冷却时间限制，默认 5 分钟内最多发送一次。
- 管理员恢复 AI 时必须二次确认。
- 恢复成功后，只有客户之后发送的新消息由 AI 回答；人工期间积压的旧消息不得补答。

默认 5 分钟通过配置项控制，不写死在界面：

```text
CUSTOMER_SERVICE_HUMAN_SLA_SECONDS=300
CUSTOMER_SERVICE_HUMAN_FALLBACK_COOLDOWN_SECONDS=300
```

## 3. 范围

### 3.1 本阶段包含

- 持久化人工接管时间、最后客户消息、最后人工回复和最后托底时间。
- 识别 Chatwoot 的人工公开回复，并与本项目自己的 AI 出站消息区分。
- 持久化 `human_wait` 等待阶段，Worker 重启后继续计时。
- 超时后的安全分类、RAG 托底或等待提示。
- 运维看板人工会话列表、SLA 状态、Chatwoot 跳转和恢复按钮。
- 受运维密钥保护的人工会话查询与恢复 API。
- 恢复时的旧任务清理、冲突保护、幂等和操作审计。
- 对应单元、集成、真实 Chatwoot 和浏览器验收测试。

### 3.2 本阶段不包含

- 多租户管理员账号、细粒度 RBAC 或独立客服账号体系。
- 自动把会话重新分配给另一名 Chatwoot 客服。
- 修改 Chatwoot 源码或在 Chatwoot 内嵌自定义按钮。
- 知识库批量上传、版本管理或文档审核页面。
- 多服务器队列、Redis、Celery、RQ 或 PostgreSQL。

真实商家知识录入仍沿用现有链路：源资料经 Docling 转换为 Markdown，发布到 Dify 数据集，完成问答评测后才投入客服使用。本阶段只复用当前已发布的 RAG 能力。

## 4. 状态与数据模型

### 4.1 会话状态

在现有 `conversation_states` 表上做向后兼容的增量迁移，新增可空字段：

| 字段 | 用途 |
| --- | --- |
| `handoff_reason` | 最近一次转人工原因的稳定分类 |
| `human_since` | 进入人工模式的 Unix 时间戳 |
| `last_customer_message_id` | 人工模式下最近客户消息的 Chatwoot ID |
| `last_customer_message_at` | 人工模式下最近客户消息时间 |
| `last_human_reply_message_id` | 最近一次有效人工公开回复的 Chatwoot ID |
| `last_human_reply_at` | 最近一次有效人工公开回复时间 |
| `last_fallback_at` | 最近一次等待提示或安全托底时间 |
| `ai_resume_cutoff_message_id` | 恢复 AI 时 Chatwoot 已存在的最大消息 ID，用于拒绝迟到的人工期旧事件 |

会话模式仍只保留 `ai` 和 `human`，避免新增难以解释的第三种所有权状态。“正常等待”“即将超时”“已超时”由时间字段动态计算，不作为新的持久化模式。

### 4.2 持久任务阶段

在现有任务阶段中新增 `human_wait`：

```text
queued
  -> generating
  -> human_wait
  -> generating
  -> ready_to_deliver
  -> delivering
  -> completed
```

`inbound_jobs` 增加消息事件时间，事件时间优先取 Chatwoot 的 `created_at`，本地入队时间仍单独保留。事件时间用于判断人工回复与客户消息的先后关系；SLA 截止时间从本地成功接收入队的时间计算，避免远端时钟偏差或迟到事件缩短人工处理窗口。

Worker 首次发现会话处于人工模式时，把任务放入 `human_wait`，并把 `available_at` 设置为本地入队时间加 SLA。任务领取结果需要保留 `claimed_from_stage`，使处理器能够区分普通 `generating` 与从 `human_wait` 到期进入的安全托底流程。仅领取或等待不增加 Dify 生成尝试次数，实际调用 Dify 时才按现有规则计次。

有效人工回复会立即结束该回复时间之前仍处于 `human_wait` 的任务，无需等待计时器到期。相同会话继续遵守现有严格顺序，不同会话仍可并行处理。

### 4.3 操作审计

新增不含客户正文的 `conversation_control_events` 表，记录：

- `conversation_id`
- `action`：`human_wait_notice`、`human_timeout_reply`、`ai_resumed`
- `result`：`succeeded` 或 `failed`
- 稳定 `error_code`
- `created_at`

审计记录不得保存消息正文、API Key、Webhook 签名、请求头或远程响应全文。

## 5. Webhook 与人工活动识别

现有签名校验、256 KiB 限制和账户校验保持不变。Webhook 在规范化事件后分为两条本地路径：

1. 客户 `incoming` 公开文本消息继续进入持久队列，并更新最后客户消息时间。
2. Chatwoot 人工用户发送的 `outgoing` 公开消息记录为人工活动。

本项目生成的出站消息使用 `ai-cs:` 开头的稳定 `source_id`，不得被记为人工回复。只有发送者类型为 Chatwoot `User`（或等价的人工用户类型）、公开且非系统的 `outgoing` 文本消息才算有效人工回复；Bot、自动化、私密消息、系统消息、其他账户和非文本事件继续忽略。

人工活动路径只写 SQLite，不调用 Dify 或 Chatwoot，因此仍满足 Webhook 快速响应要求。人工回复记录成功后，结束该回复之前的 `human_wait` 任务并更新 `last_human_reply_at`。

入站和人工回复都使用 `(Chatwoot created_at, message_id)` 组成的事件顺序；若 Webhook 缺少有效事件时间，则使用通过签名校验的接收时间作为兼容回退。字段更新使用单调最大值，避免重复或乱序 Webhook 把活动时间倒退，也避免同一秒内的消息顺序不明确。

如果入站 `message_id` 不大于 `ai_resume_cutoff_message_id`，说明它属于恢复前的迟到 Webhook 或对账回补：只做幂等完成记录，不创建可生成回复的任务。由此保证恢复 AI 后不会补答人工期间的旧消息。

## 6. 超时托底流程

Worker 领取到期的 `human_wait` 任务后按以下顺序处理：

1. 如果会话已经恢复 AI，则把该旧任务安全结束，不发送消息。
2. 如果人工回复时间不早于客户消息时间，则安全结束任务。
3. 如果仍在托底冷却期内，则安全结束任务，避免重复刷屏。
4. 先执行现有本地高风险转人工规则：
   - 投诉或法律问题
   - 支付或账户安全
   - 用户主动要求人工
5. 命中高风险规则时发送固定等待提示，保持人工模式。
6. 未命中高风险规则时调用 Dify：
   - 得到有依据的普通答案时发送带有“AI 临时协助”语义的托底回答。
   - Dify 返回知识缺口、转人工标记或发生错误时发送固定等待提示。
7. 成功投递后更新 `last_fallback_at` 并写入操作审计，会话继续保持人工模式。

客户可见托底消息使用独立稳定标识：

```text
ai-cs:<incoming_message_id>:human-fallback
```

Worker 在不确定投递是否成功时先按 `source_id` 查询 Chatwoot，沿用现有幂等投递规则，不重复发送。

## 7. 运维 API

新增两个受现有 `X-Operations-Key` 保护的接口：

```text
GET  /v1/operations/human-conversations
POST /v1/operations/conversations/{conversation_id}/resume-ai
```

### 7.1 人工会话列表

列表只返回运维必要字段：

- 会话编号
- 转人工原因和时间
- 最后客户消息时间
- 最后人工回复时间
- 最近托底时间
- 当前等待秒数
- SLA 状态：`normal`、`due_soon`、`overdue`
- 是否存在阻塞任务
- Chatwoot 会话链接

不返回客户问题正文、联系人姓名、电话、邮箱或订单信息。

如果最近客户消息已经有时间不早于它的人工回复，则当前等待秒数为 0，状态为 `normal`。否则按最新未获人工回复的客户消息计算：未达到 SLA 的 80% 为 `normal`，达到 80% 但未超时为 `due_soon`，达到或超过 SLA 为 `overdue`。托底消息不等同于人工回复，因此不会把已超时状态改回正常。

### 7.2 恢复 AI

恢复流程为：

1. 验证运维密钥和正整数会话编号。
2. 确认本地会话存在；已是 AI 模式时返回幂等 `already_ai`。
3. 预检查是否存在 `generating`、`ready_to_deliver`、`delivering`、`retry_wait` 或 `failed` 等不可安全取消的任务；存在时返回 HTTP 409。
4. 从 Chatwoot 读取会话当前标签和已存在的最大消息 ID，只移除 `ai_handoff`，保留其他标签。无法取得消息截止 ID 时不继续恢复。
5. 在一个 SQLite `BEGIN IMMEDIATE` 事务内重新检查任务状态，结束 `queued` 和 `human_wait` 旧任务，清空 Dify 上下文、转人工原因及人工活动字段，写入 `ai_resume_cutoff_message_id`，并把模式改为 `ai`。该事务必须通过共享同一数据库连接的协调方法完成，不能跨两个 Store 连接伪装成一个事务。
6. 写入 `ai_resumed` 审计事件，返回 `resumed`。

Chatwoot 标签操作先于本地 AI 状态切换。如果 Chatwoot 失败，本地仍保持人工模式；如果 Chatwoot 成功而本地事务失败，本地也仍保持人工模式。后一种情况下标签可能已经移除，但 AI 不会误接管，管理员重试即可完成恢复。

## 8. 运维看板交互

运维看板新增“人工接管会话”区域，每行显示：

- 会话编号
- 转人工原因
- 最近活动
- 等待时长和 SLA 状态
- “打开 Chatwoot”链接
- “恢复 AI”按钮

状态视觉规则：

- `normal`：中性状态。
- `due_soon`：接近 5 分钟时使用警示色。
- `overdue`：超过 SLA 时使用明确危险色，但不能只依赖颜色表达。

点击“恢复 AI”后显示二次确认：

> 恢复后，客户下一条新消息将由 AI 回复；人工期间的旧消息不会补答。

确认时禁用当前行按钮，避免重复提交。成功后从列表移除并显示结果；HTTP 409、Chatwoot 故障或其他失败必须给出可操作提示，不能静默失败。桌面和 360px 移动布局均需可用。

## 9. 错误处理与恢复

- 运维密钥缺失或错误：HTTP 401，不执行任何操作。
- 运维功能未配置：HTTP 503。
- 会话不存在：HTTP 404。
- 存在不可安全取消的活动或失败任务：HTTP 409，保持人工模式。
- Chatwoot 认证错误：返回脱敏错误，不修改本地状态。
- Chatwoot 网络、限流或 5xx：返回可重试错误，不修改本地状态。
- SQLite 事务失败：回滚本地状态，AI 不接管。
- 重复恢复：返回 200 和 `already_ai`，不重复写入成功事件。
- Worker 在等待或投递中退出：依靠 SQLite 租约、`human_wait` 和稳定 `source_id` 恢复。
- Dify 在托底时失败：不把任务标记为知识库成功回答，改为发送固定等待提示并保持人工模式。

所有持久化和日志错误只使用稳定分类，不保存远程响应全文。

## 10. 测试设计

### 10.1 单元与状态测试

- 会话活动字段增量迁移和读写兼容。
- `human_wait` 进入、到期领取、人工回复提前结束和 Worker 租约恢复。
- `human_wait` 不增加 Dify 生成尝试次数。
- 高风险规则只产生等待提示。
- 普通知识问题产生一次托底回答并保持人工模式。
- 冷却期内不重复发送。
- AI 出站事件不会被误判为人工回复。
- 恢复事务只结束可安全取消的旧任务。
- 恢复前创建但延迟送达或被对账回补的消息不会在恢复后触发 AI 补答。

### 10.2 API 测试

- 人工会话列表的认证、隐私字段和 SLA 状态。
- 恢复成功、重复恢复、会话不存在、活动任务冲突和失败任务冲突。
- Chatwoot 标签失败时本地模式不变。
- 标签已移除但本地仍为人工时可以重试恢复。

### 10.3 浏览器测试

- 人工会话列表加载、空状态和错误状态。
- 正常、即将超时和已超时不只依赖颜色区分。
- 二次确认可取消。
- 成功恢复后移除当前行。
- 失败提示可理解且按钮恢复可操作状态。
- 桌面和 360px 移动视口无溢出或遮挡。

### 10.4 真实链路验收

使用可覆盖的短测试 SLA，不在自动化测试中真实等待 5 分钟：

1. 客户转人工，人工在 SLA 内回复，确认 AI 不托底。
2. 人工停止回复，客户发送普通 FAQ，超时后只出现一条有知识依据的 AI 托底答案。
3. 客户发送高风险问题，超时后只出现等待提示。
4. 管理员从运维看板恢复 AI，确认旧消息不补答，下一条新消息由 AI 正常回答。
5. 重启 Worker，确认等待任务和幂等投递仍然正确。

完成后重跑现有单元测试、RAG 8/8、直接客服 E2E、真实 Chatwoot Widget E2E、运维浏览器测试和 Compose 校验。

## 11. 验收标准

- 人工会话不会因为 Worker 重启丢失 SLA 计时。
- SLA 内人工回复时不出现 AI 插话。
- 超时后的普通 FAQ 最多产生一条有依据的托底回复。
- 高风险或知识不足问题不由 AI 编造答案，客户至少收到一条等待提示。
- 管理员能在看板查看全部本地人工模式会话并安全恢复指定会话。
- 恢复后人工期间的旧消息不补答，客户下一条新消息恢复正常 RAG 回答。
- Chatwoot 或 SQLite 故障不会让本地会话误切换到 AI。
- 客户正文、密钥、签名和远程响应全文不进入人工会话列表、审计记录或错误日志。
- 不新增生产依赖、外部队列或多服务器行为。
