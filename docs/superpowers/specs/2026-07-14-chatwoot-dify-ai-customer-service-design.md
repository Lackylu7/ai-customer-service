# Chatwoot + Dify AI 客服设计规格

日期：2026-07-14

## 1. 背景

项目已经完成 Docling 文档解析、Dify 知识库入库和电商客服 RAG 检索验证。下一阶段需要形成客户可实际使用的客服闭环：客户从网页咨询，AI 基于企业知识回答，必要时在同一会话中转交人工客服。

第一版面向单企业电商场景，演示企业为“星河优选”。Chatwoot 提供网站聊天窗口和人工客服工作台，Dify 负责知识检索与 DeepSeek 生成，自研 FastAPI 服务负责两者之间的业务编排。

## 2. 目标

- 客户通过 Chatwoot 网站聊天窗口发起咨询。
- 普通知识问题由 Dify 检索“星河优选客服知识库”，再由 DeepSeek 生成回答。
- AI 回答必须受知识库内容约束，无法确定时不得编造。
- 投诉、支付争议、账号安全、明确要求人工等场景自动转人工。
- AI 与人工在同一个 Chatwoot 会话中连续服务客户。
- Webhook 重试不会造成重复回复，AI 自己发出的消息不会触发回复循环。
- 密钥仅保存在服务端环境变量中，不写入代码、日志或文档。

## 3. 非目标

- 不自研网站聊天窗口和人工客服后台。
- 第一版不支持多企业租户、计费、套餐和企业自助注册。
- 第一版不接入微信、邮件、WhatsApp 等额外渠道。
- 第一版不处理图片、语音和附件消息的智能识别。
- 第一版不直接修改 Chatwoot 或 Dify 源码。

## 4. 总体架构

```text
客户网页
  -> Chatwoot Website Inbox
  -> message_created Webhook
  -> FastAPI AI 编排服务
  -> Dify Chatflow
  -> Dify 知识库 + DeepSeek
  -> FastAPI AI 编排服务
  -> Chatwoot outgoing 消息 / 人工接管
```

现有 Docling 服务保持独立，只负责把企业文档转换为结构化 Markdown 并发布到 Dify 知识库，不参与在线对话请求。

## 5. 组件职责

### 5.1 Chatwoot

- 提供网页聊天插件、联系人和会话管理。
- 通过 `message_created` Webhook 把客户新消息发送给 AI 编排服务。
- 保存 AI 和人工客服的完整消息记录。
- 使用 `ai_handoff` 标签标识需要人工处理的会话。
- 人工客服直接在 Chatwoot 工作台回复客户。

### 5.2 Dify Chatflow

- 接收客户问题和稳定的终端用户标识。
- 使用现有“星河优选客服知识库”执行知识检索。
- 调用已配置的 DeepSeek 聊天模型。
- 使用客服提示词约束回答：只依据检索内容，不确定时明确说明并建议人工处理。
- 返回最终回答和检索元数据；应用密钥仅供 AI 编排服务调用。

### 5.3 FastAPI AI 编排服务

- 暴露 Chatwoot Webhook 接口。
- 使用原始请求体、时间戳和 Chatwoot Webhook 密钥验证 HMAC-SHA256 签名，并校验事件结构。
- 过滤非客户文本消息、私密备注和 AI/人工发出的 outgoing 消息。
- 按 Chatwoot 消息 ID 去重。
- 维护 Chatwoot 会话与 Dify 会话的映射。
- 执行确定性的人工转接规则。
- 调用 Dify 并把回答发送回 Chatwoot。
- 在异常或低可靠场景下停止 AI，并给会话添加人工接管标签。

### 5.4 SQLite 状态存储

第一版为单实例部署，使用 Python 标准库 SQLite，不新增数据库依赖。

数据包括：

- `processed_messages`：Chatwoot 消息 ID、处理状态和处理时间，用于幂等去重。
- `conversation_states`：Chatwoot 会话 ID、Dify 会话 ID、当前模式（`ai` 或 `human`）和更新时间。

数据库不保存 Chatwoot 或 Dify 的 API Key，不额外复制完整聊天内容。未来扩展为多实例时迁移到 PostgreSQL。

## 6. 消息处理流程

1. 客户在网站聊天窗口发送文本消息。
2. Chatwoot 向编排服务发送 `message_created` 事件。
3. 编排服务验证访问令牌、事件类型、消息方向和消息内容。
4. 编排服务使用消息 ID 执行幂等检查；已处理事件直接返回成功。
5. 如果会话已经处于人工模式，编排服务不调用 Dify，也不自动回复。
6. 如果消息命中人工转接规则，编排服务发送一条转接提示并将会话切换为人工模式。
7. 其他消息调用 Dify Chatflow；首次请求创建 Dify 会话，后续请求复用对应的 `conversation_id`。
8. Dify 返回回答后，编排服务通过 Chatwoot API 发送 outgoing 消息。
9. 处理结果写入 SQLite，供后续幂等和上下文复用。

## 7. 人工转接规则

以下场景直接转人工，不交给模型自行决定：

- 用户明确表达“转人工”“人工客服”“找客服”等意图。
- 投诉、威胁、法律纠纷或媒体曝光相关表达。
- 支付失败、重复扣款、盗刷、账号被盗等资金或账号安全问题。
- Dify 请求超时、服务不可用或返回无效内容。
- Dify 明确表示知识库没有可靠答案。

转接动作：

1. 向客户发送简短提示，说明正在转接人工客服。
2. 保留会话原有标签并追加 `ai_handoff`，避免覆盖其他业务标签。
3. 将本地会话状态设置为 `human`。
4. 后续客户消息仅进入 Chatwoot，不再触发 AI 回复。

第一版通过移除 `ai_handoff` 标签并重置本地状态恢复 AI 服务，不自动根据人工客服的一次回复恢复 AI。

## 8. 错误处理

- Webhook 参数不合法：返回 4xx，不调用外部服务。
- 重复消息：返回成功，不再次发送回复。
- Dify 超时或 5xx：记录不含敏感信息的错误，转人工。
- Chatwoot 回复失败：对可重试错误执行一次短重试；仍失败则保留失败状态，避免把消息标记为成功。
- 标签更新失败：不阻断转接提示，但本地状态仍切换为人工，避免 AI 继续回复。
- SQLite 暂时不可写：返回 5xx，让 Chatwoot 后续重试，避免失去幂等保护。

日志只记录事件 ID、会话 ID、处理结果、耗时和错误类型，默认不记录完整客户消息、API Key 或 Authorization 请求头。

## 9. 安全设计

- 按 Chatwoot 官方签名格式校验 `X-Chatwoot-Signature` 和 `X-Chatwoot-Timestamp`，使用常量时间比较，并拒绝超过 5 分钟的旧请求以降低重放风险。
- Chatwoot API Token、Dify App API Key 通过 `.env` 注入，仅在服务端使用。
- API 错误对外返回通用消息，具体异常只写入经过脱敏的本地日志。
- Webhook 请求限制最大正文大小，只接受 JSON。
- 正式上线时由 HTTPS 反向代理公开 Webhook，Docling、Dify 和内部数据库不直接暴露到公网。

## 10. 测试策略

采用测试驱动方式实现，优先覆盖用户可见行为和公共接口：

- 正常客户消息调用 Dify 并向 Chatwoot发送一次回复。
- outgoing、私密备注、空文本和无关事件被忽略。
- 同一个消息 ID 重复投递时只处理一次。
- 同一 Chatwoot 会话复用 Dify `conversation_id`。
- 明确转人工、投诉和支付安全问题不调用 Dify。
- Dify 超时、错误或空回答触发人工转接。
- 转人工后后续消息不再触发 AI。
- 添加 `ai_handoff` 时保留已有 Chatwoot 标签。
- Chatwoot 发送失败时不把消息标记为成功。
- 使用真实本地 Dify、Chatwoot 和知识库完成端到端验收。

## 11. 验收标准

- 客户可以从网页聊天窗口完成至少一轮正常知识问答。
- 连续追问能够保持会话上下文。
- 现有 8 条 RAG 评估用例继续全部通过。
- 输入“我要转人工”后，客户收到转接提示，会话出现 `ai_handoff` 标签，AI 不再回复。
- 模拟 Dify 不可用时系统自动转人工，不向客户暴露内部错误。
- 重放同一 Webhook 不产生重复 Chatwoot 消息。
- 所有新增单元和集成测试通过，三个本地服务健康检查通过。

## 12. 实施边界

本阶段只完成本地可验证闭环：Dify Chatflow、AI 编排服务、Chatwoot Website Inbox/Webhook、网页聊天入口和端到端测试。服务器、域名、HTTPS、监控告警和生产数据备份在本地闭环通过后进入下一阶段。
